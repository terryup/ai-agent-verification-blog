1. 先定义测试 Agent 的职责

测试 Agent 的核心职责不是“替模型下结论”，而是把一次交付变成可运行、可观察、可复查的验证闭环。

在 Harness 项目里，可以把测试 Agent 理解成一个验证编排者。它接收需求、测试意图或回归用例，调用 Harness 暴露的动作工具，驱动真实系统运行，再把控制面结果、媒体证据、本地指标、工具调用记录和最终报告串起来。

开发 Agent

负责实现、修改和说明，把代码交付出来。

测试 Agent

负责选择场景、调度工具、串起验证闭环。

本地 Evaluator

负责稳定判断：断言、阈值、评分和候选异常。

诊断 Agent

基于证据解释异常，提出原因假设和下一步建议。

角色应该负责什么设计边界
开发 Agent 实现需求、修改代码、补充说明 交付后的运行证据交给独立 Harness 生成
测试 Agent / 自测 Agent 选择验证场景、调度工具、收集证据、汇总报告 不绕过工具直接想象系统状态
本地 Evaluator 执行确定性判断，如断言、阈值、格式、帧率、进程状态 负责高信号筛选，不承担复杂语义解释
诊断 Agent 在证据窗口上提出原因假设、调用工具验证、给出排查建议 所有结论必须能回到证据和工具调用
一句话：测试 Agent 应该像一名有工具、有记录、有边界的验证编排者，而不是一个只输出“通过/失败”的聊天入口。

2. 为什么它要放在 Harness 里

Agent 协作开发后，最容易缺失的不是代码说明，而是运行态证据。尤其在 capture-service 这类音视频项目里，接口返回成功只能说明控制面可达，不能说明真实采集链路、媒体质量、音频信号、进程稳定性都符合预期。

Harness 天然适合承载测试 Agent，因为它连接了三类资源：被测系统的控制面、业务运行时的证据面，以及报告和回归资产的沉淀面。

控制系统 通过 HTTP/RPC/GUI 驱动真实 Worker 和业务会话。
观察运行 拿到响应、流包、帧、音频指标、进程状态。
稳定评估 先用断言、阈值、评分规则过滤高信号问题。
Agent 诊断 围绕候选异常调用工具，压缩成可读解释。
沉淀资产 输出报告、证据索引和可复跑用例。
Harness 能力给测试 Agent 带来的价值capture-service-harness 示例
控制被测系统 Agent 可以通过受控工具创建真实会话，而不是只读代码 HTTP/RPC 创建、销毁 capture session，枚举设备
采集运行证据 验证结果可以回放和复查 RTSP/fMP4、RPC StreamPacket、JPEG 帧、音频指标
沉淀测试资产 同一个场景可以被人、CI 和 Agent 复用 Markdown 用例、Runner、HTML 报告
限制工具边界 Agent 的探索范围可控，输出结构稳定 frame/video/audio/stream/code tools，`submit_report` schema

3. 为什么不直接让 Claude Code / Codex 做 P2P 测试

Claude Code、Codex 这类开发 Agent 可以辅助探索和排查，但不适合作为唯一的 P2P 验证闭环。截止本文发布时，LLM 的不稳定性、上下文漂移和工具执行不确定性仍然无法 100% 解决。

这里的 P2P 测试指的是：开发 Agent 直接临时操作被测系统、观察结果、判断通过与否，并把自然语言结论当作交付证据。它在调试阶段很有价值，但作为团队可复用的验证基础设施，会遇到几个明显边界。

输出不完全确定

同一目标下，模型的计划、工具选择和判断口径可能随上下文变化。

运行态链路很长

音视频、进程、网络、时序和设备状态都可能影响一次测试结果。

证据容易丢失

临时观察如果没有统一证据仓，后续 review 很难复查原始事实。

职责边界会混

同一个开发 Agent 自己实现、自己验收，容易缺少独立验证层。

方案适合做什么不适合作为什么
Claude Code / Codex 直接 P2P 探索问题、临时调试、补充上下文、生成候选测试思路 最终交付证据、稳定回归门禁、可审计质量结论
Harness 内测试 Agent 调度标准工具、采集证据、本地评估、输出结构化报告 承担全部人工判断，或跳过真实系统运行
设计结论：开发 Agent 可以参与测试设计和异常解释，但稳定验证应落到 Harness：用固定工具、固定证据格式、固定 evaluator 和固定报告 schema，把模型的不稳定性隔离在可控边界内。

4. 五条核心设计原则

原则一：先证据，后解释

测试 Agent 先驱动系统运行，拿到响应、日志、媒体片段、指标和工具 trace，再进行解释。没有证据的结论不能进入报告。

原则二：确定性判断前置

断言、阈值、进程状态、帧率、亮度、对比度这类稳定计算，应由本地 evaluator 完成。模型只处理需要上下文和推理的部分。

原则三：工具最小权限

Agent 只能调用 Harness 注册的工具。每个工具都有输入 schema、超时、预算和返回结构，避免无边界探索。

原则四：报告可追溯

报告中每个判断都要能追到原始证据、计算指标或工具调用。团队成员看到报告时，知道下一步该复查哪个窗口、哪个文件、哪次调用。

原则五：用例资产化

测试意图不能只存在于对话里。高价值场景应沉淀为 Markdown、JSON、OpenSpec task 或 CI 入口，让验证能重复运行。

5. 推荐的七层架构

一个可维护的测试 Agent 不应把所有能力塞进一个 prompt。更合适的做法是分层：上层负责意图和编排，下层负责真实动作和证据，中间用确定性 evaluator 降噪，最后再让 Agent 做诊断和报告。

先定义入口 明确验证来自 PR、OpenSpec、CLI、GUI 还是 Agent 交付钩子。
再定义工具 把 Harness 能力封成 action：HTTP、RPC、AV、process、wait。
建立证据仓 统一保存响应、日志、帧、片段、指标和工具 trace。
注册 Evaluator 把断言、阈值、质量维度和评分规则沉到代码里。
接入诊断 Agent 只在候选异常出现时调用模型，并强制结构化报告。

报告层不是简单收尾，而是把一次运行转化为团队资产：将执行步骤、证据路径、指标、诊断结果和后续建议写入 HTML/JSON/Markdown 报告，并把高价值场景反哺为可复跑用例。

架构思想：Agent 是控制面的一部分，不是事实来源。事实来源应来自 Harness 工具和被测系统；Agent 的价值在于规划、选择工具、解释证据和压缩上下文。

6. Agent 本身怎么设计

真正落地时，可以先把测试 Agent 看成一个带状态的工程控制回路，而不是一段 prompt。它的每一步都有输入、输出和可审计记录。

搭建时不要从“写一个大 prompt”开始，而要先把 Agent 运行所需的外壳搭好：输入契约决定它验证什么，工具契约决定它能做什么，证据仓决定它能留下什么，Evaluator 决定哪些判断不需要模型参与，输出 schema 决定团队如何消费结果。 

receive test intent
  → build verification plan
  → check environment and prerequisites
  → execute Harness actions
  → store evidence
  → run deterministic evaluators
  → diagnose candidate anomalies
  → submit structured report
设计对象需要定义清楚什么为什么重要
输入契约 目标、范围、环境、前置条件、预算、停止条件 让 Agent 知道验证什么，以及什么时候停止
工具契约 action 名称、参数 schema、超时、权限、返回结构 让执行可控、可记录、可复现
证据仓 响应、日志、截图、帧、片段、指标、工具 trace 的保存路径 让报告能被人复查，也能被后续 Agent 继续使用
Evaluator 注册表 断言表达式、质量维度、阈值、评分规则、跳过规则 让稳定判断沉到代码里，减少模型随意性
输出 schema 总体结论、分维度结果、证据索引、风险项、下一步建议 让报告格式稳定，方便 review、CI 和历史对比

测试 Agent 可以拆成三种协作角色。小项目可以由一个 Agent 扮演多个角色，大项目建议显式拆开，方便限制权限和复用能力。

Agent 角色输入输出关键约束
Planner Agent 需求说明、diff、OpenSpec、历史用例 验证计划：场景、前置条件、工具清单、停止条件 只产计划，不直接伪造执行结果
Executor Agent 验证计划和 Harness tool registry 执行 trace、原始证据、结构化 step result 只能通过工具运行系统，所有动作要可记录
Diagnosis Agent 候选异常、证据窗口、本地指标、工具结果 根因假设、置信度、修复建议、`submit_report` 不重复基础检测，必须调用结构化报告工具收尾

当前 capture-tester 中的 `runAnalysisAgent` 更接近 Diagnosis Agent。它的系统提示明确要求“本地检测已经发现异常，重点是根因调查”，并通过 `submit_report` 强制输出结构化报告；工具注册表只提供 frame、video、audio、stream 和可选 code tools。 

local anomaly
  → build system prompt with available tools
  → choose targeted tool calls
  → inspect stream/frame/audio/code evidence
  → call submit_report
  → merge into session summary

这种设计的关键是把 Agent 放在“证据之后、报告之前”。它不负责制造事实，只负责把事实组织成可理解、可行动的解释。

7. 证据链和判断边界

测试 Agent 的文档、prompt 和报告都要明确区分四类信息：事实、指标、解释、决策。混在一起，团队就很难判断报告是否可信。

层级产物判断边界
事实 HTTP/RPC response、sessionId、streamUrl、Worker pid、文件路径 证明系统实际返回了什么
证据 帧、音频指标、fMP4 片段、StreamPacket、日志 证明运行过程中观察到了什么
指标 断言结果、帧率、亮度、对比度、RMS、clip、内存采样 证明某些可计算条件是否满足
解释 异常原因假设、代码路径、工具分析结果 说明现象可能为什么发生，需要置信度
决策输入 报告结论、风险说明、下一步建议 用于 review、修复、回归和验收协作
落地建议：报告不要只写“通过/失败”。至少要包含执行步骤、关键证据、异常窗口、本地指标、Agent 工具调用、最终建议。

8. 音视频业务验证如何落地

音视频是测试 Agent 很适合介入的领域，因为业务效果依赖真实运行：有流不等于画面好，有帧不等于不卡顿，有音频轨不等于有有效声音。

设计这类 Agent 时，可以把音视频验证分成三段：真实链路取证、确定性筛选、上下文诊断。

阶段设计目标典型实现
真实链路取证 证明被测服务真的创建了会话并产生媒体输出 RTSP 拉流、RPC callback 收包、fMP4、JPEG 抽帧、AudioMeter
确定性筛选 快速发现高信号候选异常，减少模型调用噪声 帧率、亮度、过曝、极低对比度、音频 RMS、削顶、进程状态
上下文诊断 解释异常是否与启动阶段、场景内容、流时序、编码参数或代码路径相关 frame/video/audio/stream/code tools + `submit_report`

这里最重要的边界是：黑画面、静止画面、静音这类现象不能只靠一个阈值直接解释成缺陷。测试 Agent 要先保留窗口证据，再结合时间段、启动状态、流包、编码信息和代码路径判断它属于场景内容、正常初始化、链路异常，还是实现问题。 

create session
  → collect stream evidence
  → run local evaluator
  → if anomaly changes: run diagnosis agent
  → submit structured report
  → generate session summary

9. 如何融入当前 Harness 流程

`capture-service-harness` 已经具备这套架构的核心雏形。它不是单个脚本，而是一个围绕 capture-service 的验证平台。

融入 Harness 的关键，是把测试 Agent 接到已有验证链路的“编排层”，而不是让它绕开 Harness 自己操作系统。Agent 负责选择场景和解释异常，Harness 负责真实执行、证据采集和可重复报告。

交付触发 开发 Agent 完成变更后，选择 smoke、回归或 GUI 实时分析入口。
Runner 编排 CLI/GUI 将任务转成标准 action，交给 StepExecutor 或 analyzer。
真实执行 通过 HTTP/RPC/媒体链路驱动 Worker，而不是只读代码。
证据评估 收集响应、帧、流包、音频指标，再用本地规则筛选。
报告回流 异常交给诊断 Agent，最终报告进入 review 和后续回归。
架构层当前组件说明
意图入口 Electron GUI、`capture-tester test [suite]`、OpenSpec/rules 支持交互式分析和声明式回归两种入口
动作工具 `StepExecutor` 的 `http/rpc/av/process/wait` 前缀 把测试动作做成可路由、可替换的工具接口
控制面 HTTP adapter、RPC client、双 socket push stream 驱动真实 Worker 和采集会话
证据采集 `streamPump`、`ffmpegRunner`、`SegmentCapture`、`AudioMeter` 采集预览、帧、音频指标和流包信息
本地评估 `LocalDetector`、assertion evaluator、scoring model 做快速筛选和结构化分数
诊断 Agent `runAnalysisAgent`、tool registry、`submit_report` 围绕异常窗口做工具化调查
报告层 HTML report、window result、session summary 将运行过程沉淀为可复查资产

10. 当前能力边界

设计文档要把“已经落地”和“应该补齐”讲清楚。当前状态可以这样理解：

能力当前状态说明
GUI 实时视频分析主链路 已落地主链路 `SegmentCapture → LocalDetector → runAnalysisAgent → SessionSummary` 已形成帧窗口分析闭环
音频指标链路 已有采样能力，快检待闭合 `ffmpegRunner` 与 `AudioMeter` 能产出 RMS、clip、silence 等指标；GUI 本地快检还未统一接入音频判断
声明式回归框架 框架已搭，能力在补齐 Markdown parser、runner、executor、assertion、report 已有；CLI 当前主要接入 HTTP action
Agent 工具化诊断 核心链路已落地 工具包括 frame、video、audio、stream、可选 code investigation，并要求通过 `submit_report` 收敛输出
统一质量模型和 CI 化 待收敛 CLI AV Judge、GUI LocalDetector、Analysis Agent 的维度和阈值需要进一步统一

结语

设计测试 Agent 的关键，是把模型放到合适的位置：让 Harness 产生事实，让 evaluator 做稳定判断，让 Agent 负责计划、工具选择、异常解释和报告压缩。

capture-service-harness 的经验说明，这套架构尤其适合音视频这种强运行态、强业务语义的项目。只要证据链、工具边界和输出 schema 设计清楚，测试 Agent 就能从一次性的对话助手，变成团队可复用的工程基础设施。

最终目标：团队不只是拥有一个会跑测试的工具，而是拥有一套“需求变更 → 验证计划 → 真实运行 → 证据采集 → 工具诊断 → 可复查报告”的 Agent 化自测体系。
