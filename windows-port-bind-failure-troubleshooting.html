Windows 上端口起不来怎么办？

一个两三百次才撞一次、撞上就只能整机重启的端口问题，背后通常是三类原因。下面是通用的排查思路，以及在安装阶段把端口提前占下来、从根上避开的做法。

1. 起因

之前有个服务部署到 Windows 上，偶尔起不来——大概两三百次里会撞上一次，日志里报端口占用。麻烦的是一旦撞上，重启服务没用，只能整机重启才能恢复。

一开始以为是代码崩了，查了半天才发现是端口的事，而启动时又没接住这个异常，进程直接挂掉，被系统判定崩溃、自动重启，再起、再挂，表现就是“一直报错”。修完之后顺手把这类问题的排查方式整理出来。下面讲的都是 Windows 上端口起不来的通用排查逻辑。

2. 端口起不来有几种可能

第一反应往往是“谁占了我的端口”。这没错，但只对了一半。Windows 上端口绑定失败，背后其实有三类完全不同的原因，查错方向也不一样：

真被进程占着

最常见，也最好查。netstat 能直接看到占用者。

落进系统保留区间

netstat 根本看不到占用者，但就是绑不上。这是“撞一次只能重启”的元凶。

TIME_WAIT 残留

上次连接没释放干净，频繁重启时出现。

把这三类分清楚，排查就不会瞎试。下面一类一类讲，每类都给可以直接复制来跑的命令。

3. 被进程占用了，怎么揪出来

最直白的情况。先拿端口号去查谁在占，假设端口是 52781：

netstat -ano | findstr :52781

输出最后一列就是占用这个端口的 PID。拿到 PID 之后反查是哪个程序：

tasklist /FI "PID eq 12345"

确认是残留进程或冲突服务，直接干掉：

taskkill /PID 12345 /F

PowerShell 可以一条龙完成查询和识别：

Get-NetTCPConnection -LocalPort 52781 | Select LocalAddress,LocalPort,State,OwningProcess
Get-Process -Id (Get-NetTCPConnection -LocalPort 52781).OwningProcess

不想敲命令的话，资源监视器（resmon → 网络 → 侦听端口）和 Sysinternals 的 TCPView 都能可视化看谁在监听哪个端口。

最常见的占用者其实是自己上次的残留进程。上次崩溃没退干净，新实例又起不来，卡在死循环。这种情况优先怀疑自己。

4. netstat 看不到的占用：系统保留区间

这是 Windows 专属的坑，也是这篇文章最想讲的部分。

有时候会遇到一种诡异情况：netstat 里这个端口干干净净，没有任何进程在监听，但程序一绑就失败，报地址占用。折腾半天找不到凶手。

凶手往往不是某个进程，而是系统自己把这段端口“预留”走了。Hyper-V、WSL2、Docker Desktop、WinNAT 这些组件在启动时，会向系统动态保留大段端口区间，留给它们自己用。只要你的端口落在这段区间里，哪怕没有任何进程在监听，绑定也会失败。

怎么确认？查系统当前排除（保留）了哪些端口区间：

netsh int ipv4 show excludedportrange protocol=tcp
netsh int ipv6 show excludedportrange protocol=tcp

输出是一段一段的范围，比如：

起始端口    结束端口
----------  ----------
50000       50059
...

如果你的端口正好落在某个区间内，原因就找到了。

经验信号：新机器、或者新装了 Docker / WSL 之后，某个一直好好的端口突然用不了了，基本就是这个。

为什么前面说“只能整机重启才能恢复”？因为这种动态保留是系统在启动时分配的，一旦分到你的端口上，它会一直占着，重启服务、杀进程都没用——这些保留区间不属于任何进程，taskkill 根本无处下手。只有重启机器，系统重新分配动态区间，才有可能这次不撞上。这也是它发生率低（两三百次一次，纯看运气）但一旦中招就很顽固的原因。

5. TIME_WAIT 残留

服务频繁重启时还会遇到一种：端口刚被释放，还没完全回收，卡在 TIME_WAIT 状态（Windows 上大概几分钟）。新实例这时候去绑就会失败。

同样先 netstat 看状态：

netstat -ano | findstr :52781

如果看到端口处于 TIME_WAIT，那就是它了。处理很简单——要么等几分钟，要么在监听端口上打开地址复用选项，让端口能被立刻重新绑上。

注意 Windows 上地址复用的语义。它比较“宽松”，允许同一端口被多个 socket 绑定，用的时候要心里有数，别把真正的重复绑定给掩盖了。

6. 把端口提前占下来

前面三类都是“出了问题再查”。但如果是自己部署的服务、端口是固定的，其实可以在安装阶段就把它保护好，从根上避开占用——尤其是第四节那种随机中奖、只能重启的情况，预防比排查划算得多。

思路是利用 Windows 的端口排除机制——就是第四节提到的那个“坑”，反过来用。在安装阶段、服务启动之前，主动把这个端口（或一段端口）加进系统的排除区间：

netsh int ipv4 add excludedportrange protocol=tcp startport=52781 numberofports=1

这样一来，系统在动态分配端口时就不会再碰它，Hyper-V 之类的组件也抢不走，服务起来绑这个端口就是稳的。

* 前提：先把端口从动态保留里腾出来。如果这个端口已经落在 Hyper-V / WSL / Docker 的动态保留区间里，上面这条 add 会直接失败。这时候要先停掉 Windows 的 NAT 服务（停了它，那些动态保留区间才会释放），加完自己的预留，再把 NAT 服务启回来： 
net stop winnat
netsh int ipv4 add excludedportrange protocol=tcp startport=52781 numberofports=1
net start winnat

启回来的 NAT 服务会重新分配动态区间，而这次它会避开你已经预留的端口。注意 net stop winnat 会短暂影响 WSL / Docker / 虚拟机的网络，所以这套操作放在安装阶段、服务还没起的时候做最合适，别在运行中搞。

具体逻辑上还有几个要点：

  • 先删后加。上一次安装可能已经预留过同一段区间，直接加会冲突。所以每次先尝试删除这个区间（删失败也无所谓），再重新添加，保证干净：
netsh int ipv4 delete excludedportrange protocol=tcp startport=52781 numberofports=1
netsh int ipv4 add excludedportrange protocol=tcp startport=52781 numberofports=1
  • 时机要对。端口预留必须在服务启动之前完成，否则服务起的时候端口还没被保护，照样可能被别人抢走。顺序是：预留端口 → 再启动服务。
  • 要留排查痕迹。预留命令的返回码和输出要记到安装日志里。预留失败一般是因为端口已经被别的排除区间覆盖、权限不够（这条命令需要管理员权限），或者 NAT 服务没停干净，有日志下次出问题一眼能看出来。

这套做法的好处是，把“排查问题”前置成了“预防问题”——不依赖运行时去抓异常、去重试，而是在部署阶段就把端口环境收拾干净。对于固定端口的常驻服务，这是最省心的方案。

7. 排查顺序

真出了问题，按这个顺序走，基本不会绕远路：

  1. 先 netstat -ano | findstr :端口 找有没有进程占着——有就 taskkill 处理掉。
  2. netstat 干干净净却绑不上——netsh int ipv4 show excludedportrange protocol=tcp，看端口是不是落在保留区间里。
  3. 频繁重启场景——看是不是 TIME_WAIT，等几分钟或开地址复用。
记住一点：netstat 看不到占用者，不代表端口真的空闲。在 Windows 上，这往往正是排查的转折点。
