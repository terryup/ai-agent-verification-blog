AI 采集流协议怎么选？

同样是把音视频从采集服务送到业务侧，四种协议解决的不是同一个问题。AI 如果主要消费 TS 切片，HLS 或 HTTP-TS 往往比 RTSP 更直接；如果消费帧、时间戳和关键帧，私有 RTC 才是更合适的主通道。

协议选型最容易陷入一个误区：先问哪个协议延迟最低、生态最好、最容易接。但对 AI 业务来说，更重要的问题是：算法到底消费什么？是连续实时流、TS 容器、服务端切好的分片，还是带时间戳和关键帧标记的编码包？

本文的核心结论：如果 AI 业务的输入单位就是 TS 切片，优先看 HLS 或 HTTP-TS；如果 AI 业务需要帧级控制、低延迟、时间戳对齐和关键帧管理，优先看项目内私有 RTC；RTSP 则更适合作为标准实时流兼容层。

1. 四种协议的原理

HTTP-TS、HLS、RTSP 和私有 RTC 都能承载音视频，但它们的基本模型完全不同：有的是播放协议，有的是传输封装，有的是实时控制协议，有的是业务数据通道。

HLS

播放列表 + 分片

服务端持续生成 .m3u8 和 .ts 或 fMP4 分片，客户端轮询播放列表并下载最新分片。

HTTP-TS

HTTP 承载 TS 流

客户端通过一个 HTTP URL 读取 TS 形态的数据流，链路比 HLS 更直接，但没有 m3u8 的索引语义。

RTSP

实时流控制

RTSP 负责 DESCRIBE、SETUP、PLAY 等会话控制，媒体数据通常通过 RTP 连续传输。

RTC

业务包回调

项目内私有 RTC 更像 RPC_CALLBACK：不返回 URL，而是订阅 StreamPacket。

HLS：服务端先切片，再让客户端按列表取片

HLS 的核心不是低延迟，而是 HTTP 化的稳定分发。服务端把连续媒体流切成一段段媒体分片，同时维护一个播放列表。客户端不断刷新 .m3u8，再按列表下载分片。

HTTP-TS：不强调播放列表，强调 TS 流的直接消费

HTTP-TS 可以理解为通过 HTTP 输出 TS 形态的连续媒体数据。它通常比 HLS 少一层播放列表轮询，链路更直接；但它也不像 HLS 那样天然提供分片索引、窗口列表和回放管理。

因此，HTTP-TS 更适合“我需要 TS 封装，但我不一定需要服务端帮我管理一堆可回放分片”的场景。AI 服务可以持续读取 TS，再按自己的窗口策略做二次切片、缓存或投递。

RTSP：先控制会话，再接收实时媒体

RTSP 是很多摄像头、NVR、播放器和算法组件都支持的实时流协议。客户端先获取媒体描述，再建立媒体通道，最后开始拉流。它的价值在于标准生态和实时拉流，而不是服务端切片。

DESCRIBE 获取 SDP 或媒体描述 知道有哪些 track、编码格式和传输参数。
→
SETUP 建立媒体通道 准备 RTP over UDP/TCP 等传输方式。
→
PLAY 开始实时拉流 客户端持续接收音视频数据。

私有 RTC：业务直接订阅编码包

项目内私有 RTC 不是标准 WebRTC，更接近当前接口里的 RPC_CALLBACK。它不把输出包装成播放器 URL，而是通过订阅接口持续推送媒体包。包里可以带上 timestamp_ms、seq、payload_format、is_keyframe 等字段。

这类通道对播放器不一定友好，但对 AI 很友好：AI 可以看到时间戳、关键帧、轨道类型和序号，能更容易做窗口聚合、丢包检测、A/V 对齐和关键帧恢复。

2. 它们真正的差异

协议差异不是“谁高级谁低级”，而是“谁把哪一层工作提前做掉”。HLS 把切片和索引提前做了；RTSP 把实时拉流标准化了；HTTP-TS 把 TS 封装放到 HTTP 上；私有 RTC 把播放器语义拿掉，直接把业务需要的包暴露出来。

协议 核心模型 延迟倾向 最大优势 主要代价
HLS m3u8 播放列表 + TS/fMP4 分片 偏高，通常受分片长度和缓冲影响 天然分片、HTTP 友好、便于回放和分发 不适合强实时闭环
HTTP-TS HTTP URL 持续输出 TS 数据 中低，通常低于传统 HLS 接入简单，保留 TS 封装，适合实时消费 缺少 m3u8 的片段索引和回放管理
RTSP RTSP 控制 + RTP 媒体传输 低 标准生态成熟，第三方算法和工具易接 不是切片协议，复杂网络下维护成本更高
私有 RTC 订阅业务媒体包，例如 StreamPacket 最低或最可控 帧级控制、时间戳、序号、关键帧语义清楚 客户端要适配私有协议，通用生态较弱
注意：“延迟低”不等于“一定适合 AI”。如果 AI 任务是异步按片分析，稳定切片和可追溯可能比毫秒级实时更重要。反过来，如果 AI 任务是课堂实时提醒、画面质量即时检测，分片协议的稳定性就不一定抵得过私有 RTC 的帧级控制。

3. AI 切片怎么理解

讨论 AI 切片时，最关键的是区分“传输切片”和“算法切片”。这两个词听起来都叫切片，但工程含义完全不同。

切片类型 本质 更适合的协议 原因
传输切片 服务端直接产出 TS/fMP4 分片 HLS 天然有分片文件和 m3u8 索引，便于按片消费、回放和追溯。
TS 流式消费 业务侧持续读取 TS，再自行按时间窗口切 HTTP-TS 保留 TS 封装，HTTP 接入简单，少了 HLS playlist 轮询。
算法窗口切片 AI 根据时间戳、关键帧、事件窗口聚合帧 私有 RTC 直接拿到包、时间戳、序号和关键帧语义，窗口可控性最好。
标准流后置切片 先拉实时流，再由 AI 或中间层切片 RTSP 适合算法只支持标准流 URL 的情况，但切片成本后移。

需要服务端已经切好的 TS 片段：选 HLS

如果 AI 的输入、存储、上传或回放链路都是围绕一段段媒体分片组织的，HLS 是更自然的选择。它不只是给你 TS 数据，还给你分片边界、播放列表和片段生命周期。

只需要 TS 形态的实时数据：选 HTTP-TS

如果 AI 只是希望输入是 TS 容器，但窗口大小、缓存策略、投递节奏由算法服务自己决定，HTTP-TS 会比 HLS 更轻，也通常更接近实时。

所以，“AI 需要做切片”不能直接等价为“必须用 HLS”。如果切片边界、索引、回放和片段管理都希望由服务端提供，HLS 更好；如果只是希望拿到 TS 容器，然后 AI 侧按自己的逻辑切窗口，HTTP-TS 更合适。

对当前 AI 业务的修正建议：如果大多数任务真的围绕 TS 切片处理，选型优先级应从“私有 RTC / RTSP”前移到“HLS / HTTP-TS”。私有 RTC 仍然适合低延迟、帧级和关键帧可控的任务，但不应强行替代已有 TS 切片链路。

4. AI 业务怎么选

实际选型可以用一个问题树收敛：AI 是要片、要流，还是要帧？这个问题比“哪个协议更先进”更有效。

业务诉求 优先选择 不优先选什么 判断依据
AI 输入就是 TS 分片 HLS RTSP 后置切片 HLS 已经把分片、索引和窗口管理前置到服务端。
AI 需要 TS 容器，但自己决定窗口 HTTP-TS 完整 HLS 链路 省掉 m3u8 轮询，读取一条 TS 流即可。
第三方算法只支持标准 URL RTSP 私有 RTC ffmpeg、OpenCV、GStreamer 等生态更容易接。
实时检测、帧级分析、关键帧窗口 私有 RTC HLS HLS 的分片和缓冲会牺牲实时性；私有通道能暴露包级元数据。
人工预览 + AI 分析并存 双通道 单协议强行覆盖所有场景 人看视频和 AI 算数据的诉求不同，应拆开优化。

5. 放到项目里怎么落地

在当前项目里，流媒体协议会返回不同形态的 stream_url：HLS 是 .../hls.m3u8，HTTP-TS 是 ...live.ts，RTSP 是 rtsp://...。私有 RTC 则更接近 RPC_CALLBACK：创建会话后 stream_url 为空，通过 SubscribePackets 接收数据。

项目内可以把输出分成两类 URL 拉流 vs 业务包订阅

URL 拉流类

RTSP、HLS、HTTP_TS 都启动媒体服务并返回 URL。它们适合播放器、第三方算法、HTTP 消费链路，以及需要标准协议接入的系统。

包订阅类

RPC_CALLBACK 不返回流媒体 URL，而是推送 StreamPacket。它适合需要 timestamp_ms、seq、is_keyframe 的 AI 实时处理链路。

因此，AI 业务可以按“算法输入契约”分层接入，而不是所有算法都统一压到同一个协议上。

第一层 算法是否要求 TS 片段？ 如果要求按片上传、按片落盘、按片回放，优先 HLS。
→
第二层 算法是否只需要 TS 流？ 如果自己切窗口、自己管缓存，优先 HTTP-TS。
→
第三层 算法是否要帧级控制？ 如果需要关键帧、序号、低延迟闭环，优先私有 RTC。
不要把“AI 需要切片”一概翻译成“AI 需要私有 RTC”。如果切片产物是 TS 文件或 TS 容器，HLS/HTTP-TS 能少走很多后置转封装逻辑。私有 RTC 的优势在于包级控制，而不是天然替代 TS 切片协议。

结尾：一个判断口诀

协议选型可以压缩成一句话：人看视频，优先播放器协议；AI 算数据，优先看输入契约。

要服务端切好的片 选 HLS，它负责切片、索引、回放窗口和片段生命周期。
要 TS 形态的实时流 选 HTTP-TS，它保留 TS 封装，也让 AI 侧自己控制窗口。
要标准实时 URL 选 RTSP，它最大价值是生态兼容和通用工具链接入。
要帧级元数据和低延迟控制 选私有 RTC，它把时间戳、序号和关键帧语义交给业务。
最终建议：当前 AI 如果更多围绕 TS 切片工作，主路径应优先验证 HLS 和 HTTP-TS。HLS 适合“服务端切好并管理分片”；HTTP-TS 适合“AI 侧实时读取 TS 并自行切窗口”。私有 RTC 保留给低延迟、帧级、关键帧可控的实时 AI 场景，RTSP 保留给通用生态兼容。
