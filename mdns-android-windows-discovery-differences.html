mDNS 在 Android 与 Windows 上有什么不同：为什么 Android 收到设备消息会慢

同样是局域网服务发现，Windows 侧通常是应用自己发包、收包、整理结果；Android 侧更多是把发现交给系统，再等系统回调。这个差异会直接影响设备上线、下线消息到达应用的速度。

1. 先看问题：协议一样，体验不一样

Android 和 Windows 都可以用 mDNS/DNS-SD 做局域网设备发现，但写代码时会明显感觉到：Windows 更像一次主动扫描，Android 更像等系统通知。

mDNS 本身并不复杂：设备在局域网里广播服务信息，客户端通过多播查询和响应找到它。一个设备通常会拆成几类 DNS 记录返回，比如 PTR 告诉你服务实例，SRV 告诉你主机名和端口，A/AAAA 告诉你 IP，TXT 放一些额外信息。

问题在于：这些记录不是一次性完整返回的，可能先到一部分，晚点再到另一部分。Windows 和 Android 对这件事的处理方式不一样，于是设备消息到达应用的时间也不一样。

Windows/C++ 自实现

应用自己打开 socket，自己发送查询，自己收包，然后把零散记录拼成完整设备信息。复杂，但什么时候扫、扫多久都由应用决定。

Android NsdManager

应用告诉系统“帮我找这个服务”，系统找到后再通过 listener 回调通知应用。简单，但什么时候通知、通知是否及时，应用不能完全控制。

核心判断：差异不在 mDNS 协议，而在平台给应用的控制权。Windows 侧更接近“我现在去扫一遍”，Android 侧更接近“系统发现了再告诉我”。

2. Windows 怎么做：应用自己扫

在当前 C++ 实现里，Windows 侧使用 mdns 库直接处理查询和响应。可以把它理解成应用自己发起一次扫描：

枚举网卡获取本机 IPv4 地址
打开 socket每个地址绑定一个客户端 socket
发送 PTR查询目标 service type
select 收包在 timeout 内持续接收
聚合记录输出完整服务快照
auto start_time = std::chrono::steady_clock::now();
auto timeout_duration = std::chrono::milliseconds(timeout_ms_);

while (std::chrono::steady_clock::now() - start_time < timeout_duration) {
  select(nfds, &readfs, nullptr, nullptr, &tv);
  mdns_query_recv(sock, buffer.data(), buffer.size(), queryCallback, this, query_id);
}

这个模型很好理解：应用给自己一个时间窗口，比如 3 秒。在这 3 秒里，应用不断收 mDNS 包，收到多少算多少，最后把能拼完整的设备返回出去。

它的缺点是代码复杂。应用要处理多网卡、socket、超时、重复包、记录乱序。优点也很直接：想更快发现，就可以缩短扫描间隔；想收得更完整，就可以拉长接收窗口。实时性是可以通过参数调的。

Windows 侧不是天然更实时，而是更可控。应用自己决定扫描频率和超时时间，所以可以在“发现速度”和“资源消耗”之间做取舍。

3. Android 怎么做：系统帮你找

Android 常见做法是通过 NsdManager 发起服务发现。应用调用 discoverServices() 后，不再直接接触 socket 和 DNS 包，而是等系统通过 DiscoveryListener 回调。

nsdManager.discoverServices(
  "_edgeBoxAgent._tcp.",
  NsdManager.PROTOCOL_DNS_SD,
  discoveryListener
);

典型事件流是：

discover启动系统发现会话
onServiceFound收到服务出现事件
resolve解析 host、port、属性
onServiceResolved拿到可连接信息
onServiceLost收到服务消失事件

这套封装的好处很明显：应用不用自己收包，不用解析 DNS 记录，也不用关心多网卡。系统告诉你发现了服务，你再去 resolve，拿到 host、port 等信息。

但代价也在这里：应用拿到的不是原始 mDNS 包，而是系统处理后的回调。从设备发出广播，到应用收到 onServiceFound 或 onServiceLost，中间多了一层系统调度和缓存。

4. Android 为什么会慢：不是协议慢，是中间层多

Android 上设备消息不够及时，很多时候不是 mDNS 协议慢，而是应用没有直接控制发现过程。系统什么时候发查询、什么时候认为服务丢失、什么时候把回调派发给应用，都不完全由应用决定。

影响点表现对实时性的影响
onServiceFound 不是完整结果 发现服务后通常还要再 resolve 收到 found 之后，还要等 resolve 成功才能真正使用
系统托管 discovery 应用不能直接控制 query 重发节奏和收包窗口 应用很难像 Windows 自实现那样精确压低扫描延迟
回调调度 事件需要经过系统服务和应用线程执行 设备已经上线，但应用层 callback 可能稍后才到
缓存与丢失判断 onServiceLost 依赖系统内部状态判断 设备已经下线，但 lost callback 不一定马上到
Wi-Fi 多播策略 多播接收可能受系统过滤、省电和网络状态影响 后台、弱网、网络切换时延迟更明显

所以 Android 的关键问题不是"有没有 callback"，而是 callback 到底代表什么。它代表系统在某个时刻通知应用“我发现服务状态变了”，不代表应用看到了每一个 mDNS 包，也不代表这是设备变化发生的第一时间。

不要把 Android NSD callback 当成实时设备消息。onServiceFound 和 onServiceLost 更像系统整理后的通知，而不是设备上线/下线瞬间的原始信号。

这也是为什么一些 Android 侧实现看起来会“慢半拍”：服务端可能已经广播了，mDNS 包也可能已经在网络里了，但应用收到的是系统封装、调度之后的事件。

5. 上线和下线怎么判断

Windows 和 Android 还有一个很实际的差异：设备列表是怎么维护出来的。

Windows：快照差异

scan N 得到一组完整服务记录。
scan N+1 再次扫描得到新的服务记录。
diff 通过前后两次结果比较，判断谁新增了、谁消失了。

Android：事件累积

onServiceFound 把服务加入本地设备列表。
onServiceResolved 补齐 host、port 等连接信息。
onServiceLost 从本地设备列表移除，或者标记为可能离线。

Windows 的快照模型很直观：我扫一次，得到一份列表；过一会儿再扫一次，再得到一份列表。两份列表一对比，就知道哪些设备新增、哪些设备消失。

Android 的事件模型更依赖系统回调：系统告诉你 found，就加入列表；系统告诉你 lost，就移除列表。问题是，如果 lost 来得晚，本地列表就会短时间保留一个已经离线的设备。

这就是 Android 侧容易出现“不够实时”的地方。上线慢，是 found 和 resolve 之间有延迟；下线慢，是 lost 不一定马上到。最终看到的不是设备状态本身，而是系统什么时候把状态变化通知给应用。

结尾. 不要把 callback 当实时状态

同样是 mDNS，Android 和 Windows 的差异并不只是 API 写法不同。Windows 侧更像应用主动扫描，复杂但可控；Android 侧更像系统代替应用发现设备，简单但不够可控。

如果只是展示“附近有哪些设备”，Android 的封装通常够用。但如果设备列表会影响连接、路由或健康判断，就不能把 onServiceFound 和 onServiceLost 当成强实时状态。

更稳的判断方式是：mDNS 只负责发现入口，设备是否真的可用，还要结合连接探测或健康检测。尤其在 Android 上，callback 到达应用的时间，本身就是一个不稳定因素。
