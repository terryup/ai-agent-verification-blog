Windows 锁屏后采集为什么会黑屏：Session、Desktop、DXGI 与 SYSTEM 进程身份

锁屏不是屏幕停了，而是 input desktop 变了。能不能继续采集，取决于进程身份、所在 Session，以及采集线程能否切到新的 Desktop 后重建 DXGI。

1. 锁屏黑屏不是低能耗问题

Windows 锁屏后桌面采集变黑，常见误解是“屏幕关了”或“显卡没有输出”。真正的问题通常不是显示器，而是采集线程失去了当前 input desktop。

对基于 DXGI Desktop Duplication 的采集程序来说，锁屏瞬间最关键的变化是：系统把输入桌面从用户日常工作的 Default 切到安全桌面 Winlogon。旧的 duplication 实例会失效；如果进程没有权限打开新的 input desktop，就无法重建采集链路。

一句话：锁屏黑屏的根因不是“没有帧”，而是“进程没有资格进入当前正在显示的安全桌面”。

2. 先看懂 Session、Window Station、Desktop

Windows 图形界面不是一个平面概念。它至少有三层：Session、Window Station、Desktop。

Session N：用户登录会话

真正有用户交互、GPU 上下文、音频端点和输入桌面的地方。远控、录屏、桌面采集通常要落在这里，而不是 Session 0。

Default Desktop 用户日常桌面，应用窗口主要在这里。
Winlogon Desktop 锁屏、UAC、Ctrl+Alt+Del 等安全界面。
Screen-saver Desktop 屏保等特殊场景使用。
Session 0：服务隔离会话

服务默认在这里运行。它可以有很高权限，但不是用户正在看的图形会话。把采集进程简单放到 Session 0，通常拿不到用户桌面的真实画面。

锁屏动作的关键不是释放桌面资源，而是系统调用类似 SwitchDesktop() 的机制，把当前 input desktop 从 Default 切到 Winlogon。

3. DXGI Desktop Duplication 为什么会失效

DXGI Desktop Duplication 的性能很好，但它有一个硬前提：采集线程必须绑定到当前可访问的 input desktop。

锁屏发生时，典型链路是这样的：

用户 Win+L 系统进入锁屏流程。
切到 Winlogon input desktop 改变。
Duplication 失效 AcquireNextFrame 返回 DXGI_ERROR_ACCESS_LOST。
尝试重建 需要打开新的 input desktop。
权限失败 普通用户进程打不开 Winlogon Desktop。

Winlogon Desktop 默认不是普通用户进程可以随便打开的对象。采集程序即使捕获到 DXGI_ERROR_ACCESS_LOST，如果 OpenInputDesktop() 被 ACL 拒绝，后面的 SetThreadDesktop() 和 D3D 重建就都走不下去。

黑屏的关键断点：不是没有处理 DXGI_ERROR_ACCESS_LOST，而是处理到一半发现没有权限进入新的安全桌面。

4. 为什么是 SYSTEM @ Session N

要穿透锁屏，需要同时满足两个条件：

条件为什么必须满足错误做法
SYSTEM 身份 有资格打开 Winlogon Desktop，完成 OpenInputDesktop / SetThreadDesktop。 普通用户进程留在 Session N，锁屏后重建失败。
位于用户 Session N 保留用户图形会话、GPU 上下文、设备可见性和音频端点。 服务进程待在 Session 0，权限高但不在用户桌面。

这就是 SYSTEM @ Session N 的含义：身份是 SYSTEM，但进程位置在用户登录会话里。

实现上常见路径是：Root 服务在 Session 0 运行，找到目标用户会话里的 winlogon.exe，复制它的 SYSTEM token，再用 CreateProcessAsUserW 把 Worker 投递到对应用户 Session。

Root service (Session 0, SYSTEM)
  -> find winlogon.exe in active user session
  -> OpenProcessToken + DuplicateTokenEx
  -> CreateProcessAsUserW(token, desktop = "winsta0\\default")
  -> Worker runs as SYSTEM @ Session N
这个组合很精确：SYSTEM 解决安全桌面权限，Session N 解决图形与设备上下文。少任何一半都不够。

5. 真正的穿透发生在恢复循环里

进程跑成 SYSTEM @ Session N 只是前置条件，不是最终答案。采集线程还必须在运行时处理桌面切换。

while (running) {
  frame = duplication.AcquireNextFrame();

  if (frame == DXGI_ERROR_ACCESS_LOST) {
    destroy_duplication_and_d3d();

    HDESK desk = OpenInputDesktop(0, FALSE, GENERIC_ALL);
    SetThreadDesktop(desk);

    recreate_d3d_device();
    recreate_duplication();
    continue;
  }

  output(frame);
}

锁屏和解锁都会触发 desktop 切换，所以恢复逻辑不能只处理一次。它应该是一个稳定的 try-recover 循环：发现 duplication 失效，销毁旧资源，切到当前 input desktop，重建 D3D 和 duplication，再继续输出。

验收标准要用用户语言描述：Win+L 锁屏 30 秒，远端拉流不黑屏，帧率不掉为 0；解锁后继续恢复到 Default Desktop。

6. 为什么不拆成双 Worker

一个看似更安全的方案是拆成两个进程：CaptureWorker 用 SYSTEM 负责采集，UserWorker 用普通用户身份负责音频、外设和业务模块。

它符合“最小权限”的直觉，但放到音视频采集系统里，代价很高。

单 Worker

一个 SYSTEM @ Session N 进程承载采集、音频、外设和信令。锁屏穿透、用户切换和崩溃恢复都只有一个状态机。

双 Worker

Capture 和业务拆进程后，需要 IPC、共享内存、双进程生命周期、跨进程音频同步和版本兼容。

维度单 Worker双 Worker
锁屏穿透一个进程内处理 DXGI + Desktop 切换CaptureWorker 仍然要做同样逻辑
PCM 音频同进程分发，延迟和抖动可控需要跨进程共享内存、同步原语和背压策略
多用户切换旧 Worker 退出，新 Session 拉起一个 Worker两个进程要同步切换、握手和恢复
调试单进程日志和调用栈双日志、跨进程时序、半通路状态
安全边界一个高权限进程，攻击面较大Capture 权限收敛，但工程代价显著上升

这里的关键判断是：如果实测证明 SYSTEM @ Session N 不破坏音频、COM、HID 和业务 SDK，那么双 Worker 的主要收益就变弱了，剩下的是一整套跨进程复杂度。

远控软件的成熟实现也基本印证这点：主流方案更倾向让一个位于用户会话的高权限进程承担采集、音频、剪贴板、文件传输等职责，而不是把低延迟媒体链路拆散。

结论：锁屏采集不是单纯的 DXGI 问题，也不是单纯的权限问题。它是 Windows 图形会话模型、进程身份、桌面 ACL 和采集链路恢复机制共同作用的结果。

真正稳的方案不是“把进程提权”这么粗暴，而是把身份、Session 位置和桌面切换恢复循环三件事同时做对：SYSTEM 身份负责进入安全桌面，用户 Session 负责保留图形上下文，采集线程负责在 desktop 切换后重建 DXGI。
