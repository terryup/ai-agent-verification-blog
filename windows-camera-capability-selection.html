Windows 摄像头给了这么多能力，到底该选哪个？

Windows 摄像头枚举出来的 capability 只是硬件说"我能吐这些"，不是系统说"我应该拿这个"。采集策略的价值，在于把一份偶然排序的能力清单，收敛成后续 pipeline 可以稳定消费、可以复用、也可以解释的 CapturePlan。

评分表不是"总代价最小算法"，而是一个局部排序器。真正的工程问题是：在多个 capability 都"能用"时，系统如何选择一个源、如何归一化它、如何让资源池判断它能不能被复用。

1. capability 不是策略

一个 Windows 摄像头通常会返回几十条能力：格式、宽高、帧率交叉组合在一起。直接拿第一条，等于把系统决策权交给了摄像头枚举顺序；按分辨率最近拿，也只是把问题缩成了一个维度。

同一个 1080p30 目标下，多个 capability 都看起来能用 区别不在能不能采，而在后续要付什么代价
H264 1920×1080 @ 30fps，压缩流；如果不是目标直通，就要走解码/再编码语义 只在直通前提下便宜
I420 1920×1080 @ 30fps，planar YUV，通常最贴近编码器输入 非直通时优先
YUY2 1920×1080 @ 30fps，packed YUV，需要内存重排或转换 可接受
RGB24 1920×1080 @ 30fps，需要 RGB → YUV 色彩空间转换 较贵
MJPEG 1920×1080 @ 30fps，逐帧 JPEG，需要解码，但没有帧间依赖 兜底

这里的核心不是"I420 一定赢过 H264"，而是同一行格式在不同阶段含义不同：H264 如果能作为目标编码流直通，它可能最便宜；如果后面还要进入普通编码 pipeline，它反而是最贵的一类输入。采集策略必须先区分这些前提，再谈排序。

格式成本只有在前提明确时才有意义。脱离直通、编码、归一化这些阶段，只说"哪个格式更便宜"，会把一个多阶段策略误解成单表排序。

2. 决策产物不是一个格式

采集策略输出的不是"选中了 I420"这么简单，而是一个 CapturePlan。真正影响后续行为的是这些字段：

CapturePlan 的关键字段 格式选择只是其中一部分
sourceCapability 记录策略认为最合适的原始候选 后续编码参数默认值会参考它
normalizedCapability 真正交给 CreateMediaSource 的采集能力 也进入 ResourcePool 的 source key
processing flags 标记是否 passthrough、是否需要 scale 它们是后续 pipeline 的路由信息
target encoder 客户端指定目标编码器和编码参数 策略补默认值，但不替客户端选择 codec
source key 由 deviceId、type、normalizedCapability 组成 决定多个 session 能否共用同一个采集源
pipeline key 在 source key 基础上加 encoder 和 passthrough 区分同源上的不同处理链路

这个结构说明了一件事：策略层不是在做"格式排行榜"，而是在把摄像头能力翻译成资源模型。真正危险的错误也不只是选错格式，而是让两个本该复用的采集源因为能力不一致无法复用，或者让两个处理语义不同的 pipeline 被错误合并。

3. 这是字典序策略，不是成本函数

当前实现的核心比较不是一个加权分数，而是字典序 tuple：

// passthrough 阶段
  (abs(targetW - cap.width),
   abs(targetH - cap.height),
   abs(targetFps - cap.framerate))
  
  // 非直通阶段
  (abs(targetW - cap.width),
   abs(targetH - cap.height),
   typeOrder,
   abs(targetFps - cap.framerate),
   detailOrder)

这意味着它不是在证明"总代价最小"，而是在表达一组强优先级判断：先保分辨率，再看格式族，再看帧率，最后才看同族细节。这个差别很重要，因为字典序策略没有单位换算，也没有说"一次缩放等于多少次色彩转换"。

字典序的好处

它简单、稳定、可解释。每一层比较都能对应一个工程偏好：分辨率不轻易牺牲；格式成本只在分辨率接近时介入；同族差异不跨越族边界。

字典序的代价

它会把字段顺序固化成强规则。比如宽高差优先于格式成本，就意味着一个分辨率更贴近但格式更贵的 capability 可能胜出。

算法的本质不是一张表，而是一组优先级承诺。数字 0、10、100 本身不重要；真正影响行为的是字段顺序，以及字段顺序背后的取舍。

4. 评分表只解决格式这一维

评分表只在非直通阶段、且宽高比较没有先把候选分出胜负时，介入格式处理成本排序。它不是入口决策，也不会覆盖分辨率和帧率字段的优先级。

typeOrder

表达格式族之间的结构性差异：planar YUV、packed YUV、RGB、帧内压缩、灰度、帧间压缩。族间差异先于同族细节。

detailOrder

表达同族内部偏好：I420、NV12、NV21 都属于 planar YUV，但仍可用更小的次序决定默认选择。

建表依据不是"格式名好不好看"，而是这个 capability 进入普通编码 pipeline 前要经历什么处理：

格式族排序的依据 注意：这不是全局成本函数，只是格式维度排序

这张表有两个边界。第一，H264/H265 在非直通阶段排在最后，不代表它们永远差；它们在目标编码格式一致时可能先进入 passthrough 候选。第二，灰度并不是处理成本最高，而是信息保真最差：丢色度是不可逆质量损失，所以它的位置不是纯性能排序。

灰度这一行不是纯处理成本排序。这里混入了第二条轴：质量损失。它的位置表达的是一个业务判断：保留色彩信息，比少做一次 MJPEG 解码更重要。

5. 归一化决定能不能复用源

评分表选出 sourceCapability 后，策略还会做一件容易被忽略、但对系统更重要的事：找一个基础分辨率，生成 normalizedCapability。

sourceCapability 策略选择的候选 例如 1920×1080 I420
→
base resolution 从非压缩能力里选基准分辨率 优先不低于目标，否则取最大
→
normalizedCapability 创建 source 时实际使用 进入 ResourcePool source key

这一步的工程含义是：采集源最好按少数稳定规格创建，然后在 pipeline 层做 scale。这样两个业务请求即使目标编码参数不同，也可能复用同一个底层 source。评分表解决的是"选哪条 capability"，归一化解决的是"这个选择能不能沉淀成可复用资源"。

格式评分解决"拿哪种输入更便宜"，归一化解决"系统里能不能少开一个采集源"。前者是局部性能，后者是资源生命周期。

6. 直通、兜底与边界

这套策略有三个容易误读的边界。它们决定了评分表什么时候生效，也决定了策略输出不能被过度解读。

边界一：passthrough 是语义，不是自动成立的零成本

策略层会在目标 codec 可以映射到摄像头压缩格式时，优先找同格式 capability，并把 isPassthrough 置真。这个标记表达的是"这条路径具备直通语义"。但后续 pipeline 是否真的跳过 Encode，必须由执行层实现。否则它只是路由标记，不是零编码承诺。

边界二：FindBestRawCapability 并不只选 Raw

非直通阶段的评分表里仍然包含 MJPEG、H264、H265。它们不是优先项，而是兜底项。这个选择很现实：如果摄像头没有理想的 raw/yuv/rgb 能力，系统宁可选一个昂贵但可用的压缩输入，也不要直接失败。

边界三：默认目标不是完全照抄客户端参数

实现里目标宽高和帧率有默认下限：小于 1080p30 的请求不会把策略目标降到更小规格。这个选择可能是为了源复用和画质余量，但它也意味着"用户请求 720p"不等于"采集源也选 720p"。

策略承诺 采集策略是一组可解释的优先级和资源复用约束，而不是追求数学意义上的全局最优。
策略边界 评分表不保证总代价最小；passthrough 也只有在执行层确实绕过编码时，才等价于零编码路径。

结尾：这套策略真正保护什么

采集策略真正保护的不是某个格式永远排第一，而是三件事：不依赖摄像头枚举顺序；在多个可用 capability 之间做稳定、可解释的取舍；让采集源具备被 ResourcePool 复用的可能。

评分表的价值，是把格式处理成本放进策略；它的边界，是它不能替代完整的采集计划。采集策略真正落地时，评分、归一化、资源 key 和 pipeline 行为必须一起看。
