1. 背景：测试用例到底写成什么

回归测试用例经常卡在一个选择上：写代码，还是写配置。

写代码，表达力强，但测试意图容易藏进实现细节里。写 YAML/JSON，机器友好，但人读起来很快变成字段堆叠。

我的选择是：用 Markdown 做一层轻量声明式 DSL。

人能读懂 标题、步骤、清理动作都直观，测试意图不被字段结构淹没。
机器能执行 固定结构可以解析成 AST，再交给执行器调度 HTTP、RPC、AV 等动作。
AI 能生成 Markdown 是大模型稳定输出的格式，适合生成、修改和复查测试资产。

适用场景很明确：API smoke、端到端主流程、音视频质量检查、稳定性压测入口，以及需要 AI 参与生成和维护的测试资产。

2. 核心设计：一个用例就是一个 Markdown 文件

# 创建设备会话

```meta
suite: api
tags: smoke, session
requires: worker, camera
timeout: 10000
```

## Steps

- action: rpc.call
  method: Capture.CreateSession
  deviceId: $cameraId
  capture: session
  assert: status == OK

## Teardown

- action: rpc.call
  method: Capture.DestroySession
  sessionId: $session.id
概念作用
meta描述 suite、tag、前置依赖、超时
Steps描述执行步骤
capture捕获步骤结果，供后续步骤使用
assert对步骤返回值做断言

解析后的模型保持简单：

interface TestCase {
  name: string;
  metadata: TestCaseMetadata;
  steps: Step[];
  teardown: Step[];
}

interface Step {
  action: string;
  params: Record<string, unknown>;
  capture?: string;
  asserts: StepAssert[];
}
第一条原则：DSL 要小，不要一开始就做成编程语言。首版不支持 if、for、宏、函数，也不支持任意脚本执行。复杂逻辑应该沉到执行器里，通过新的 action 暴露出来。

3. Action 是路由协议

action 不只是命令名，它是执行器的路由协议。

Action 前缀路由目标
http.*HTTP 客户端
rpc.*RPC 客户端
av.*音视频质量判定
process.*进程监控
wait内置等待
 
switch (prefix) {
  case 'http':
    return deps.httpRequest(method, path, body);
  case 'rpc':
    return deps.rpcCall(method, params);
  case 'av':
    return deps.avJudge(params);
  case 'process':
    return deps.processMonitor(params);
  case 'wait':
    await sleep(ms);
    return { waited: ms };
}

这个设计带来两个直接收益：新增能力时优先扩展 action，而不是改语法；HTTP/RPC/AV/Process 都通过依赖注入，执行器可以单测。

DSL 只描述“要做什么”，不要绑定“具体怎么做”。

4. 变量系统要保留类型

回归测试一定会遇到跨步骤传值：创建 session，使用 session 订阅流，再销毁 session。所以 DSL 支持 capture 和 $var。

- action: rpc.call
  method: Capture.CreateSession
  capture: session
  assert: status == OK

- action: rpc.call
  method: Capture.DestroySession
  sessionId: $session
写法行为
$session返回原始值，保留对象、数字、数组等类型
session=$session做字符串插值

不要把所有变量都转成字符串。RPC 参数、并发数、布尔开关、对象 body 都需要类型保真。

  • 未定义变量直接失败。
  • 支持对象递归插值。
  • 精确变量引用保留类型。
  • 变量作用域限定在单个用例内。

5. 断言表达式宁可简单

首版断言只支持少量运算符：

==, !=, >=, <=, >, <, contains, not_contains, all_pass
- action: http.get
  path: /devices
  assert: status == 200

- action: av.check
  type: basic
  assert: checks all_pass true

断言执行时只做两件事：从返回对象里按字段路径取值，再用简单运算符比较。

复杂判断不要塞进表达式语言。更好的方式是把复杂逻辑封装成 action，让 action 返回结构化字段，再用简单断言检查结果。

6. Teardown 必须一开始就有

资源型测试最怕脏状态。比如采集会话没有释放，后续用例可能全部失败。于是你会遇到典型问题：单独跑通过，整套跑失败。

## Teardown

- action: rpc.call
  method: Capture.DestroySession
  sessionId: $sessionId

- action: wait
  ms: 1000

Teardown 不只是清理资源，也是在描述测试用例的生命周期。

Parse读取用例
Check meta检查依赖
Run steps执行步骤
Assert断言结果
Teardown清理资源
Report生成报告

7. 报告字段要倒推设计

DSL 最终要服务于报告。步骤执行结果至少要保留：

interface StepResult {
  action: string;
  passed: boolean;
  duration: number;
  error?: string;
  captured?: Record<string, unknown>;
}
字段价值
action失败发生在哪类动作
passed汇总通过率
duration定位慢步骤
error给出失败原因
captured保留关键上下文

测试框架的价值不只是“能跑”，而是失败时能解释清楚。

8. 取舍总结

这套 DSL 的边界很清楚。

适合

  • API smoke test
  • 主流程端到端测试
  • 音视频质量检查
  • 稳定性压测入口
  • AI 生成和维护测试用例

不适合

  • 大量复杂分支逻辑
  • 精细性能 benchmark
  • 强类型协议兼容性测试
  • 复杂 mock 编排
如果一个测试场景可以被产品、测试、开发用自然语言讲清楚，就适合沉淀成 Markdown DSL。如果它主要验证内部算法细节，就留在代码测试里。

9. 可复用清单

  1. 先定义使用者：开发、测试、CI、AI 是否都会参与。
  2. 语法保持小：meta、steps、capture、assert、teardown 足够起步。
  3. Action 用前缀路由：http.*、rpc.*、av.*、process.*。
  4. 变量插值保留类型：不要把所有值字符串化。
  5. 断言表达式保持简单：复杂逻辑封装成 action。
  6. Teardown 从第一天就加入。
  7. 从报告倒推执行结果字段。
结论：Markdown DSL 的价值不在于格式新，而在于它把测试用例变成了共享资产。开发者能调试，测试同学能维护，CI 能执行，AI 也能生成和修复。

真正关键的设计原则是：Markdown 表达测试意图，结构化字段负责机器执行，复杂能力沉到 action 背后的工程代码里。这样既保留了可读性，也保住了工程边界。
