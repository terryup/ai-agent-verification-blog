AI Agent 驱动的服务迁移验证体系

把多个历史业务模块迁移合并到一个统一服务，迁移编码大量交给 AI Agent。本文记录这套迁移验证体系怎么搭——用确定性门禁约束 AI 的非确定产出，保证迁移前后行为一致。

1. 背景

近期在做一件事：把多个历史业务模块的代码迁移合并到一个统一服务里，迁移编码大量交给 AI Agent 完成。

AI 产出快，但带来一个直接问题——我怎么知道它没把旧服务的行为改坏？下面是我搭的一套迁移验证体系，用来约束 AI 的产出、保证迁移前后行为一致。

2. 问题在哪

三个难点：

难点说明
旧服务行为没有契约文档 多个历史模块迭代多年，真实行为散落在代码里，谁也说不全“正确行为”长什么样。
AI 产出是非确定的 同一个迁移任务，AI 这次和下次的写法可能不同，人工逐行 review 不可持续，也容易漏。
“行为一致”很难量化 不能靠代码 diff——实现完全可以不同，只要对外行为一样就行，但“行为一样”怎么证？
本质上这是个信任问题：怎么用确定性手段，约束 AI 非确定的产出。

3. 核心思路

把“迁移是否正确”从“读代码判断”变成“跑行为判断”：

  • 先用 golden case 把旧服务的外部行为锁成基线；
  • 让 AI 按里程碑迁移，每个里程碑跑确定性门禁（编译 → 测试 → 探针比对 → 差异报告）；
  • 门禁全过才进下一个里程碑，失败就给 AI 精准修复导航。

这套思路复用了之前在测试 Agent 上的方法论（七层架构、证据先行），场景从音视频质量验证换成了服务协议一致性验证。

4. 里程碑与四道门禁

迁移拆成 7 个里程碑，从单端点逐步到端到端、再到多产品线隔离。每个里程碑跑四道门禁，前一道失败就停，不浪费时间跑后面：

01 编译 构建新服务，连编不过谈不上行为。
02 单测 跑 C++ 测试，基础正确性。
03 探针 打真实服务，比对 golden。
04 差异 golden vs 实际，逐字段 diff。
✓ 推进 全过进入下一里程碑。

输出是结构化 JSON：整体结论、卡在哪道门、修复提示，让迁移 Agent 程序化解读，而不是让人去读日志。

5. Golden case 锁基线

迁移前，用探针把旧服务的每个端点行为采集下来，固化成 golden case。golden 是旧服务真实行为的基准，不是“理想行为”——哪怕旧行为是个 bug，迁移后也得保留，否则就是行为变更。

关键纪律：golden 不轻易改。只有确认旧服务实际行为和 golden 不一致时才更新，且必须注明原因。否则迁移 Agent 会为了“看起来更对”而偷偷改行为，这恰恰是迁移要避免的。

6. 分层探针

行为验证分四层，逐层收紧：

HTTP 端点

status code + body 结构，最外层入口。

内部 RPC（UDI）

基于命名管道的内部 RPC 通道，envelope 报文 + 字段值。

状态链

端点之间的编排顺序：授权码 → 鉴权 → 心跳 → 列表 → 超时清理。

逐字段 diff

golden 和实际响应的精确比对，定位到字段。

分层的好处是定位快：HTTP 挂了是路由问题，UDI 挂了是注册问题，状态链挂了是编排问题，字段 diff 挂了是实现细节问题。每层失败指向不同修复方向。

7. 给 AI 的失败导航

这是我觉得最值钱的一环。

每个探针 case 预置一条 fix_hint：具体文件路径 + 修复方向。Agent 失败时拿到的不是一堆堆栈日志，而是一条结构化导航：

{
  "blocked_gate": "probe",
  "file": "src/.../url_service.cpp",
  "fix_hint": "handler 校验 filesystem::exists，不存在时返回 422"
}

配合一条熔断：同一个门禁连续失败 3 次就停下来报告阻塞点，不让 Agent 无限重试空耗。

关键区别：给 AI 的是导航而非日志。精准定位 + 修复方向，比让 Agent 自己从堆栈里试错高效得多。

8. 防误报

一个会“假通过”的验证框架比没有更糟——因为你会信它。这块是踩过坑才加的。

一个验证框架最大的风险不是“报错”，而是“该报错却报通过”。几条硬规则：

  • 探针退出码非 0 必判失败。连不上服务时探针输出是空的，不判失败就会被误报成“全部通过”。
  • 漏跑等于失败。期望的 case 没采集到，不能默认通过，否则探针静默漏跑就成了漏洞。
  • 区分环境阻塞和代码错误。返回 404/502/空 往往是服务没起来或管道不可用，要标成“环境阻塞”而不是“代码 bug”，否则 Agent 会去改代码改到天荒地老。
  • 超时不掩盖。重启服务后 poll 就绪状态，超时也放行让探针报真实失败，不用固定 sleep 假装“应该起来了”。

9. 通用经验

  1. 用确定性门禁约束非确定产出。AI 负责写，门禁负责判，两件事分开。
  2. 行为基线 > 代码对照。允许实现不同，只卡外部行为一致。
  3. 给 AI 导航而不是放任重试。精准 fix_hint + 熔断，比让 Agent 看日志试错高效得多。
  4. 防误报是底线。一个会“假通过”的验证框架比没有更糟。
  5. 里程碑渐进式门禁。风险分段，早失败早止损。

10. 边界与演进

诚实说当前状态：单端点和通信集成的里程碑已通过并用于真实迁移；多产品线隔离的里程碑还在收尾。几个待补方向：把门禁接入 CI（目前本地跑）、探针容器化摆脱对真实设备的依赖、和音视频那套验证框架统一 evaluator。

最终目标：不是“有一个能跑测试的脚本”，而是让“需求变更 → 验证计划 → 真实运行 → 证据采集 → 工具诊断 → 可复查报告”这套 Agent 化自测能力，能跨场景复用。
